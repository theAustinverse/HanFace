# HanFace 網站平台實作方案與建置步驟

這份文件解決一個具體問題：妳要在哪個平台、用什麼順序、按哪些按鈕，才能把「後台自主更新 ＋ 捲動動畫 ＋ IG 動態牆」這三件事做出來，而且三年後想搬家時不會被平台綁到動不了。

---

## 0. 先講三個必須修正的既有假設

在進入方案之前，我查證後發現三件事跟先前的規劃前提有落差。這三件事會直接影響妳選哪個方案等級、花多少錢，所以先講。

### 修正一：US$16/月 那個等級（Basic）不能寫任何自訂程式碼

Squarespace 在 2025 年 2 月宣布改版方案結構，到 2026 年 2 月已在所有國家推出 **Basic / Core / Advanced** 三個方案（若當地支援 Squarespace Payments，還會多一個 Plus）。目前年繳價格約為：

| 方案 | 年繳（每月均攤） | 月繳 | 年繳總額 | 約合台幣／年 |
|---|---|---|---|---|
| Basic | US$16 | US$25 | US$192 | 約 NT$6,100 |
| Core | US$23 | 約 US$33 | US$276 | 約 NT$8,800 |
| Plus | US$39 | — | US$468 | 約 NT$15,000 |
| Advanced | US$99 | 約 US$139 | US$1,188 | 約 NT$38,000 |

（匯率以 NT$32/US$1 估算，請以刷卡當下為準。**我無法直接連上 squarespace.com 驗證官方定價頁**——這個環境的網路代理封鎖了該網域，以上數字來自多家第三方定價追蹤站的交叉比對，且它們對 Basic 的說法有 US$16 與 US$19 兩種版本。實際下單前請自己開官網確認，並確認台灣地區是否適用相同價格。）

**關鍵差異：Basic 不提供自訂程式碼注入（Code Injection）與 API 存取。** 也就是說 Basic 上妳不能加一行 CSS。這件事對我們的影響是具體的，我在第 1.3 與 1.4 節會說明哪些設定需要 CSS、哪些不需要。

### 修正二：IG 動態牆這件事在 2024 年 12 月被 Meta 動過刀

Meta 在 **2024 年 12 月 4 日** 正式關閉 Instagram Basic Display API，這個 API 就是 Squarespace 原生 Instagram 區塊過去用來抓貼文的管道。結果是：

- 原生 Instagram 區塊**沒有被下架**，仍然存在，Squarespace 也仍在維護說明文件。
- 但它現在**必須用「專業帳號」（商業帳號或創作者帳號）**才能連。個人帳號無法透過任何官方 API 取得內容。
- 2024/12/4 之後沒有重新授權過的舊連結，**不會再抓到新貼文**（會停在舊內容或空白）。
- 這條連線在社群回報中一直有「無聲斷線」的問題——它壞掉的時候不會通知妳，妳的網站上就出現一塊空白或半年前的貼文。

**這不代表要放棄 IG 牆，但代表 IG 牆必須有備援設計。** 我在第 1.6 節給三套做法。

先確認一件事：**妳的 IG 帳號是不是專業帳號（商業／創作者）？** 如果還是個人帳號，這件事現在就可以先改，免費、五分鐘，而且改成專業帳號才有洞察報告可看。

### 修正三：Squarespace 現在有原生的字體上傳功能了

過去在 Squarespace 換字體必須寫 CSS `@font-face`，現在後台有原生的自訂字體上傳器（接受 .otf/.ttf/.woff/.woff2）。這對我們**不是好消息而是誘惑**——它讓「上傳一個漂亮的中文字型」變得只要三個點擊。**請不要做這件事。** 中文字型檔 4–5MB，上傳它會摧毀妳的手機首屏。理由不變，只是現在誘惑變大了，所以我把這句話寫在這裡當防線。

## 第一部分：Squarespace 完整實作計畫

### 1.1 該選哪個方案等級

這是一個需要妳自己做的判斷，我把它拆成兩個情境。

| | **情境 A：Basic（US$192/年）** | **情境 B：Core（US$276/年）** |
|---|---|---|
| 適合什麼情況 | 妳願意接受「範本給我什麼樣式我就用什麼樣式」，色彩用內建調色盤能調到八成像就好 | 妳在意細節：中文行高、字距、按鈕圓角、藕色面上的次要文字對比度、首屏不套動畫 |
| 色票能否套用 | 可以，5 色調色盤是原生功能，不需要程式碼 | 可以，而且能用 CSS 補上調色盤放不進去的 #EAD3CB 線色與次要文字色 |
| 中文字體 | 只能靠瀏覽器預設 fallback（結果多半正確，但**妳無法控制**，Windows 訪客可能拿到細明體那類難看的結果） | 可以用一行 CSS 明確指定 `PingFang TC → Noto Sans TC → Microsoft JhengHei` 的順位 |
| 捲動動畫 | 可以（站台級動畫是原生功能） | 可以，而且能用 CSS 把首屏排除在動畫之外 |
| 原生 IG 區塊 | 可以（區塊本身不分方案，但需專業帳號） | 同左，另可用 CSS 修掉區塊預設的間距與說明文字 |
| 表單 | 可以 | 可以 |
| 年成本差額 | — | 比 Basic 多 US$84／年（約 NT$2,700） |
| 風險／代價 | **一旦上線後發現有個地方非改不可，妳必須升級才能改**，而升級是隨時可以做的，不會掉資料 | 多花 NT$2,700／年買「可修正的權利」；但也多了一個「亂貼網路上的 CSS 把網站弄壞」的風險面 |

**我的傾向：先開 Basic 做，卡住再升 Core。**

理由是：Squarespace 的方案是隨時可升級的，資料不會掉，所以「先低後高」的順序沒有懲罰，而「先高後低」會浪費錢。而且對一個剛開始的品牌，網站第一版能不能上線遠比細節完美重要。

**什麼條件下我會直接叫妳從 Core 開始：** 如果妳打算請設計師或外包做這個網站。外包一定會要 CSS 權限，開 Basic 只會讓對方在第一天就叫妳升級，中間還要重跑一次刷卡。

**一個必須先講明的注意事項：** Squarespace Scheduling（就是 Acuity，線上預約系統）**不包含在任何網站方案裡**，是完全獨立的另一筆訂閱，Emerging 方案年繳約 US$16/月（US$192/年）。妳目前沒有選線上預約，所以現在不用付這筆。但知道這個數字很重要，因為它意味著「網站 + 線上預約」的真實年成本是 US$192+US$192 ≈ NT$12,300，而不是 NT$6,100。這件事在 03 號文件（預約流程）裡已經處理過，這裡只是提醒別把成本算漏。

### 1.2 推薦三個範本，以及一句妳必須先知道的話

**先說最重要的一句：在 Squarespace 7.1 裡，範本的選擇沒有妳想的那麼要緊。**

7.1 跟舊版 7.0 最大的差別是：**所有 7.1 範本共用同一套底層引擎**。範本之間唯一的差別是「預先排好的頁面版面 + 一組預設的色彩與字體」。妳選了 A 範本之後，可以把它改成 B 範本的樣子；妳也可以刪掉範本給的所有頁面重新排。範本是起跑點，不是牢籠。

這件事的實際意義：**不要花三天糾結範本。** 選一個結構最接近妳需要的，一小時內決定，把時間花在照片和文案上——那才是真正決定網站看起來像 hince 還是像 AMUSE 的東西。

以下三個是我查證過確實存在於 Squarespace 官方範本庫的 7.1 範本：

| 範本 | 為什麼適合韓系極簡＋藕色系 | 代價／要注意什麼 |
|---|---|---|
| **Clune**（第一推薦） | 定位在 spa 與護膚類服務。大量留白、柔和字體、段落之間的轉場平順；捲動時頁首會自動隱藏，視覺干擾最少。它的預設結構就是「服務型單店」的結構，而不是「電商」的結構——這跟妳的實際需求（不賣線上商品）對上了 | 它的預設版面留給圖片的面積偏大。以妳目前只有手機隨拍的狀況，這些空位會**放大**素材的弱點。如果照片還沒拍，先用單色藕色塊 + 文字撐版，不要硬塞低品質照片 |
| **Novo**（第二推薦，也是「照片不夠時」的最佳選擇） | 版面偏格狀（style grid），設計取向是「乾淨、不擁擠、內容優先」。它比較容易做出「排版本身就是設計」的效果——這正是妳照片素材還沒到位時最需要的能力 | 格狀版面需要「數量」而非「品質」：格子空著會很明顯。如果妳只有 6 張可用照片，格數就要調到 6 的倍數，不要留半空的一列 |
| **Hester**（第三推薦，如果妳半年內就會上線線上預約） | 明確為美容沙龍設計，預設就內建了服務清單與預約行程的版位。如果妳確定要走 Squarespace Scheduling，Hester 的預設結構省下最多重排的工 | 它的預設結構假設妳「有一份完整的服務與價格清單」。如果服務項目還沒定案，這個範本會有一半的區塊空著，反而拖慢進度 |

（範本的敘述與定位來自第三方 Squarespace 設計社群的評測，不是官方文案——因為我無法直接連上官方範本庫驗證。範本名稱本身我用多個獨立來源交叉確認過確實存在。請自己開一次官方範本庫，用手機看預覽，看三分鐘，選一個。）

**另外兩個名字妳可能會在網路文章裡看到，但我不建議：** Paloma（為高單價時尚精品設計，重度依賴大幅攝影，妳現在的素材撐不起來）、Maca / Bailard（電商導向，妳不賣線上商品，用它們等於扛著一堆用不到的結構）。

### 1.3 色票怎麼套進 Squarespace 的樣式系統

Squarespace 7.1 的色彩系統是兩層的，這一點一定要先理解，不然妳會在後台找不到東西：

```
第一層：網站調色盤（Site Palette）── 5 個顏色格子
                    ↓ Squarespace 用這 5 色自動生出
第二層：區段主題（Section Themes）── 10 組配色
        （Lightest 1/2、Light 1/2、Bright 1/2、Dark 1/2、Darkest 1/2）
                    ↓ 每一個頁面「區段」指定用哪一組
```

**步驟：**

1. 進 `編輯（Edit）` → `網站樣式（Site Styles）` → `色彩（Colors）` → `編輯調色盤（Edit Palette）`
2. 把五個格子填成：

| 格子 | 色碼 | 角色 |
|---|---|---|
| 1 | `#FDF9F7` | 底色（頁面主背景） |
| 2 | `#F6E7E1` | 面色（區塊背景、卡片） |
| 3 | `#E2B4A6` | 淺藕（純裝飾：分隔線、圖標、色塊。**不放字**） |
| 4 | `#96594C` | 深藕（按鈕、連結、強調文字） |
| 5 | `#3D2E2B` | 文字 |

3. 我們的色票有七個顏色，格子只有五個。放不進去的兩個（`#EAD3CB` 線色、次要文字）處理方式：
   - `#EAD3CB` 線色：進各個區段主題，把「分隔線／邊框」欄位手動改成這個值（區段主題裡的個別元素是可以逐項覆蓋的）。
   - 次要文字：見下方 1.3.2，這個顏色有問題，要先改。

#### 1.3.1 只用三組區段主題，其他七組不要碰

十組主題全部可用，等於十種可能的配色，等於必然的不一致。**紀律規則：全站只准出現三組配色。**

| 我們的命名 | 對應到 Squarespace 主題（建議） | 背景 | 標題／正文 | 按鈕 | 連結 | 用在哪 |
|---|---|---|---|---|---|---|
| **A｜白底** | Lightest 1 | `#FDF9F7` | `#3D2E2B` | 底 `#96594C` ／字白 | `#96594C` ＋底線 | 大部分內容區段 |
| **B｜藕底** | Light 1 | `#F6E7E1` | `#3D2E2B` | 底 `#96594C` ／字白 | `#96594C` ＋**必須有底線** | 需要跟前後段落分開的區段（服務卡片、引言） |
| **C｜深藕底** | Darkest 1 | `#96594C` | `#FDF9F7` | 底 `#FDF9F7` ／字 `#96594C` | 白色 ＋底線 | 全站只用**一次**：主要行動呼籲（例如「預約諮詢」那一段） |

C 主題只用一次是刻意的。它是全站視覺最重的一塊，用兩次以上，它就不再是重點，只是壁紙。

#### 1.3.2 我要修改一個既有決定：次要文字色 `#856B65` 不合格

我把色票逐一算過 WCAG 對比度，發現一個之前沒被抓到的問題：

| 前景 | 背景 | 對比度 | AA 標準（4.5:1） |
|---|---|---|---|
| `#3D2E2B` 文字 | `#FDF9F7` 底色 | 約 13.0:1 | 通過（很充裕） |
| `#3D2E2B` 文字 | `#F6E7E1` 面色 | 約 11.3:1 | 通過 |
| `#96594C` 深藕 ＋白字 | — | 5.48:1（已知） | 通過 |
| `#96594C` 深藕文字 | `#FDF9F7` 底色 | 約 5.19:1 | 通過 |
| `#96594C` 深藕文字 | `#F6E7E1` 面色 | **約 4.51:1** | 剛好通過，只差 0.01 |
| `#856B65` 次要文字 | `#FDF9F7` 底色 | 約 4.69:1 | 勉強通過 |
| `#856B65` 次要文字 | `#F6E7E1` 面色 | **約 4.07:1** | **不通過** |

兩個具體結論：

**（一）建議把次要文字色從 `#856B65` 改成 `#6E564F`。** 這個值在白底上約 6.4:1、在藕色面上約 5.6:1，**兩種背景都安全通過**，而且它仍然是同一個藕棕色系，視覺上幾乎看不出差別（明度差約 6%）。這樣妳只要記一個次要文字色，不用記「在哪個背景上不能用哪個色」——這種規則在實際操作中一定會被忘記。

**（二）藕色面（`#F6E7E1`）上的連結一律加底線或做成按鈕，不能只靠顏色區分。** 因為 4.51:1 這個數字是「剛好」，只要日後有人把面色稍微調深一點（例如覺得太淡想加一點濃度），它就會掉到標準以下，而且沒有人會發現。加底線是零成本的保險，同時對「連結看不出是連結」這個更常見的使用性問題也有幫助。

（對比度數值是我依 WCAG 2.x 相對亮度公式計算的，可能有小數點層級的誤差。要複核的話用 WebAIM Contrast Checker：https://webaim.org/resources/contrastchecker/ ，貼兩個色碼就會直接給數字。這是免費工具，值得妳自己驗一次。）

### 1.4 中文字體怎麼設定成系統字體

先理解 Squarespace 的字體選單在做什麼：它給妳的是 **Google Fonts / Adobe Fonts 的西文字型**。這些字型檔裡**沒有中文字**。所以：

> 當網頁遇到中文字時，瀏覽器會自動掉回「使用者裝置上的預設中文字體」。

**這件事本身就是「系統字體」的行為，也就是我們想要的結果。** 但它是不受控的結果：

| 裝置 | 瀏覽器實際會拿到的中文字體 | 品質 |
|---|---|---|
| iPhone / iPad / Mac | PingFang TC（蘋方繁體） | 很好 |
| Android | Noto Sans CJK TC | 好 |
| Windows 10/11 | Microsoft JhengHei（微軟正黑體） | 可接受 |
| 舊 Windows 或設定被改過 | 可能是 PMingLiU（新細明體） | **難看，會毀掉整個韓系質感** |

最後那一列就是為什麼要寫一行 CSS。

**方法 A（Basic 方案，不寫程式碼）：** 什麼都不做，接受瀏覽器 fallback。實際上八成以上的訪客會拿到正確的字體（妳的流量 90% 來自 IG 手機，手機幾乎都會落在 PingFang TC 或 Noto Sans CJK）。**代價：** 少數桌機訪客可能看到新細明體，而妳沒有工具修它。

**方法 B（Core 方案以上，寫一段 CSS）：** 明確指定 fallback 順位。做法：`網站樣式` 完成西文字體選擇後，進 `設定（Settings）` → `進階（Advanced）` → `自訂 CSS（Custom CSS）`，貼入：

```css
/* HanFace 中文字體 fallback 順位 —— 不載入任何中文網頁字型 */
:root {
  --hf-cjk: "PingFang TC", "Noto Sans TC", "Hiragino Sans TC",
            "Microsoft JhengHei", "Heiti TC", sans-serif;
}

h1, h2, h3, h4, h5, h6,
p, li, a, blockquote, figcaption,
.sqs-block-button-element,
input, textarea, select, button {
  /* 把妳在網站樣式裡選的西文字型名稱填在第一位 */
  font-family: "在此填入妳選的西文字型名稱", var(--hf-cjk) !important;
}

/* 中文正文的行高與字距 —— 西文的預設值對中文一律太擠 */
p, li, blockquote {
  line-height: 1.85;
  letter-spacing: 0.02em;
}
h1, h2, h3 {
  line-height: 1.4;
  letter-spacing: 0.01em;
}
```

三個具體提醒：

1. **第一位一定要放西文字型名稱**，中文 fallback 放後面。這樣英文與數字用妳精選的西文字型（品牌感來源），中文用系統字體（效能來源）。順序寫反，英文也會變成系統字體，質感直接掉一級。
2. **中文不要用 font-weight 300 或更細。** PingFang TC 有真正的細體，看起來很好；但 Windows 上的微軟正黑體沒有細體，瀏覽器會用演算法硬拉細，結果是筆畫斷裂、糊掉。中文請只用 400（正常）與 600/700（粗）。這是妳在 Mac 上做設計、客人在 Windows 上看時最常出事的地方。
3. **`line-height: 1.85` 這個數字不是隨便給的。** 西文預設常在 1.4–1.6，中文方塊字在這個行高下會擠成一團豆腐。1.8–1.9 是中文長段落的舒適區。這一項調整對「乾淨純淨」的觀感提升，比換字型有效得多，而且免費。

### 1.5 捲動動畫怎麼開、以及建議開到什麼程度

**位置：** `編輯` → `網站樣式（Site Styles）` → `動畫（Animations）`。這是站台級設定，開了會套用到全站所有區段。

可選的類型：**Fade**（淡入）、**Slide**（由下滑入）、**Scale**（由小放大）、**Clip**（逐行由左裁切進入），另有 **Flex**（給標題、連結、按鈕、導覽列加上額外的動態與 hover 效果）。速度可選 Slow / Medium / Fast。

#### 我的建議設定

| 項目 | 建議值 | 理由 |
|---|---|---|
| 類型 | **Fade** | 唯一不移動元素位置的類型。移動類動畫（Slide / Scale）在慢速手機上會抖，而且會讓版面在載入時「跳」，破壞「乾淨」的第一印象 |
| 速度 | **Slow** | 慢＝貴。快速的淡入看起來像「網頁在追趕自己」，慢速淡入是精品品牌的標準做法（Aesop、hince 都是這個路數） |
| Flex | **關掉** | Flex 是 AI 生成感的主要來源。它會讓標題逐字彈跳、按鈕會呼吸、導覽列會變形。這些效果單獨看都很酷，疊在一起就是「範本感」 |
| Scale / Clip | **不要用** | Clip（逐行裁切）用在中文上特別糟——中文沒有明顯的字母基線，逐行裁切會讓字看起來像被切到一半 |
| 視差（Parallax）背景 | **不要用** | 手機上最常掉幀的效果，也是最容易被辨認為「便宜範本」的特徵 |

#### 一個關於「動畫過多」的判準

不要用「幾個動畫」來判斷，用這個問題判斷：

> **從上滑到下，訪客會不會有任何一刻在等一個東西出現？**

如果會，動畫就過多了。動畫的正確角色是「東西已經在那裡，只是溫柔地被看見」，不是「東西藏著，等妳滑到才給妳」。第二種做法會製造微小但持續的焦慮，而焦慮跟「乾淨純淨」是互斥的。

#### 首屏不要套動畫（這一項需要 CSS，也就是需要 Core）

站台級動畫會套用到**包含首屏在內**的所有區段。這會造成兩個問題：

1. 訪客從 IG 點進來的第一眼，看到的是一片空白正在淡入。這是最糟的第一印象，因為它跟「網站很慢」的體感完全一樣，訪客分不出來。
2. 首屏的主圖通常就是 LCP 元素（見第四部分）。對它套淡入動畫，會讓 PageSpeed 量到的 LCP 數字變差。

CSS 解法（貼在同一個自訂 CSS 區）：

```css
/* 首屏區段不套入場動畫 —— 讓第一眼就是完整的 */
.page-section:first-of-type [data-animation-role],
.page-section:first-of-type .sqs-block {
  opacity: 1 !important;
  transform: none !important;
  animation: none !important;
  transition: none !important;
}
```

**誠實標註：** Squarespace 的 CSS 類別名稱會隨版本改動，上面這段是依目前 7.1 常見結構寫的，不保證在妳的範本上一次就中。實測方法：貼上後存檔，用手機開網站重新整理，看首屏是否立刻完整出現。如果沒生效，把 `.page-section:first-of-type` 換成該區段在頁面上的實際區段 ID（在瀏覽器右鍵檢查元素可以看到 `id="..."`）。**如果妳在 Basic 方案上，這一段做不了**——替代做法是把首屏做得比較不依賴動畫（例如首屏就是一張滿版圖 + 一行字 + 一顆按鈕），讓淡入只影響很少的元素。

### 1.6 Instagram 區塊怎麼設定，以及放在哪裡

#### 設定步驟（原生區塊）

1. **先確認 IG 是專業帳號**（商業或創作者）。個人帳號現在無法透過官方 API 連線。若還是個人帳號，Squarespace 的連線流程會引導妳轉換，或妳在 IG App 裡自己改（設定 → 帳號類型）。
2. Squarespace 後台 → `設定（Settings）` → `第三方工具（Third Party Tools）` → `已連結帳號（Connected Accounts）` → 連結 Instagram，完成授權。
3. 回到 `已連結帳號`，點 Instagram 圖示 → 按 **`Reset Data`**（重設資料）。這一步很多人漏掉，漏掉會導致區塊抓不到新貼文。
4. 到要放的頁面，插入 **Instagram 區塊**，設定顯示張數（建議 **6 張**，兩列三欄，手機上不會拖太長）。
5. 區塊設定裡把「顯示說明文字（caption）」**關掉**——只留圖。理由見下方風險段。
6. 資料更新頻率約每小時一次，這是 Squarespace 的行為，不可調。

#### 建議放的位置：頁尾正上方，不是首屏

我同意妳的研究結論，而且理由可以講得更精確。決定位置的不是美觀，是**訪客的移動方向**：

```
訪客路徑：IG 貼文 → 點 bio 連結 → 妳的網站 → ？

若 IG 牆在首屏：      網站 →（1 秒內）→ 回到 IG →  流失
若 IG 牆在頁尾上方：  網站 → 讀服務 → 看價格 → 建立信任
                          → IG 牆（社會證明：這家店是活的）
                          → 預約按鈕                    →  轉換
```

首屏的 IG 牆是一個**出口**，頁尾的 IG 牆是一個**憑證**。同一個元件，位置決定它是漏水還是加分。

具體版位建議（首頁）：

| 順序 | 區段 | 主題 |
|---|---|---|
| 1 | 首屏：一句品牌定位 ＋ 一顆「預約諮詢」按鈕 | A 白底 |
| 2 | 我們提供什麼（3 個服務卡片，各連到服務頁） | B 藕底 |
| 3 | 品牌理念（短，三行以內） | A 白底 |
| 4 | 環境／空間照片 | A 白底 |
| 5 | **預約行動呼籲（全站唯一的深藕區段）** | C 深藕底 |
| 6 | **Instagram 牆（6 張）＋「追蹤 @hanface」文字連結** | A 白底 |
| 7 | 頁尾：地址、營業時間、聯絡方式、隱私權政策連結 | B 藕底 |

注意 IG 牆排在行動呼籲**之後**。這是刻意的：如果訪客已經滑到那麼下面，他要嘛已經按了按鈕，要嘛就是還在觀望——對觀望的人，IG 牆是「這家店真的有在營運」的證據，這時候讓他回 IG 追蹤是可以接受的次佳結果（追蹤＝日後還能觸及他）。

#### 三個必須知道的風險，以及三套備援做法

**風險一：自動 IG 牆會把 IG 上的法規風險搬到網站上。**

這是我在這份文件裡最想讓妳注意的一件事。自動抓取的意思是：**妳無法事前審核哪張圖會出現在網站上。** 如果妳日後在 IG 發了一張前後對比照，或一句「痘痘肌救星」，那張圖／那句話會自己爬到 HanFace 官網的首頁上。

而官網比 IG 更容易被檢舉、更容易被主管機關當成「品牌的正式廣告表現」來做整體綜合評價。妳的身分（美容工作室、無醫師）在這件事上完全沒有緩衝空間。

（把 caption 關掉能擋掉文字風險，但擋不掉圖片風險。）

**風險二：它會無聲斷線。** 帳號改密碼、Meta 改 API 政策、授權過期——網站上就出現一塊空白，而妳不會收到通知。

**風險三：它是妳網站上唯一依賴外部第三方的元件。** 也就是妳唯一無法自己修的部分。

| 做法 | 內容 | 成本 | 適合什麼情況 | 代價 |
|---|---|---|---|---|
| **A｜原生自動牆**（滿足妳原本的需求） | 上述步驟；caption 關閉；6 張 | 含在方案內，NT$0 | 妳的 IG 內容已經全面通過法規檢查，而且妳有紀律持續維持 | 自動抓取＝失去事前審核權；會無聲斷線；每季要自己開網站確認它還活著 |
| **B｜手動精選圖組**（我的傾向） | 用 Squarespace 的圖庫（Gallery）區塊放 6 張自選圖，每張連到對應的 IG 貼文網址。每月更新一次，10 分鐘 | NT$0 | 妳想要 100% 控制網站上出現什麼 | 不是「自動顯示最新貼文」——這一項不符合妳原本列的需求。需要妳每月花 10 分鐘 |
| **C｜第三方 IG 牆服務** | EmbedSocial、Elfsight 之類的嵌入服務，有免費層與付費層，設計控制較多、斷線通知較完整 | 免費層通常有浮水印或張數限制；付費約 US$5–15/月 | 妳確定要自動、又不能接受無聲斷線 | 多一筆月費；多一個第三方 script 拖慢首屏；多一個平台鎖定點 |

**我的傾向是 A ＋ B 的混合：先做 A（滿足自動的需求），但同時把 B 的圖庫區塊建好、隱藏起來。** 一旦 A 斷線或某張貼文不該出現在官網，妳在後台切一個開關（隱藏 A、顯示 B），30 秒解決，不用求救。

**我不建議直接推翻「自動顯示 IG 最新貼文」這個需求**——那是妳明確要的，而且它確實有價值（網站看起來是活的）。但我要妳知道自動化的真正代價是**放棄事前審核權**，而在妳的法規處境下，這個代價不小。有備援的自動化，跟沒備援的自動化，是兩件不同的事。

### 1.7 表單怎麼建、通知怎麼設

#### 建立步驟

1. 在「預約／聯絡」頁插入 **表單區塊（Form Block）**。
2. 欄位設定（**只放這些，不要多**）：

| 欄位 | 型別 | 必填 | 備註 |
|---|---|---|---|
| 姓名 | 文字 | 是 | |
| 手機 | 文字 | 是 | 提示文字寫「用於回覆預約確認」 |
| Email | Email | 否 | 選填，降低填表阻力 |
| 希望的服務項目 | 下拉選單 | 是 | 選項用妳的課程名稱，最後一項給「不確定，想先諮詢」 |
| 希望的時段 | 下拉選單 | 是 | 例如「平日上午／平日下午／平日晚間／週末」——不要做日期選擇器，那會讓客人以為時間已經被鎖定 |
| 想補充的事 | 長文字 | 否 | |
| 個資告知同意 | 勾選框 | 是 | 見下方 |

3. **不要在這張表單問任何健康問題。** 不要問過敏史、皮膚疾病、正在用的藥、是否懷孕。這些在個資法第 6 條屬於「特種個資」，原則上不得蒐集，例外之一是經當事人**書面同意**，而書面同意不能靠網路表單上的一個勾選框帶過。這些問題留到客人到店後，用一張獨立的紙本同意書處理。網站表單的角色只是「約時間」，不是「問診」。

4. 勾選框旁邊的文字要能連到完整的告知內容。建議做法：勾選框文字寫

   > 我已閱讀並同意 [個人資料蒐集告知事項]

   括號內做成連結，連到獨立的「隱私權政策」頁面，該頁面完整寫出個資法第 8 條的六款事項（蒐集者名稱、蒐集目的、個資類別、利用之期間／地區／對象／方式、當事人得行使之權利與方式、不提供將對其權益之影響）。**不要試圖把六款事項塞進勾選框旁邊那一行小字**——塞不進去，塞進去也沒人讀，而且視覺上很醜。完整條文的草稿在 04 號文件。

#### 通知設定（這一段是實務上最容易出事的地方）

Squarespace 表單的通知邏輯：**加入表單區塊的那個人，他的帳號 email 會被自動綁成收件者。** 要改，在表單區塊的 `儲存（Storage）` 分頁，把現有的 email 按 X 移除，填入妳要的地址。

`儲存` 分頁裡可以設定的管道：

| 管道 | 設定位置 | 可靠性 | 建議 |
|---|---|---|---|
| Email 通知 | Storage → Email | 中（會進垃圾信匣） | **必開。** 用一個專用的 Gmail，並在手機 Gmail App 設定「這個標籤的通知一律開啟」 |
| Google Drive（自動建一張 Google Sheet） | Storage → Additional Storage → Google Drive | **低——這條連線有大量「無聲停止同步」的社群回報，Squarespace 自己有一篇專門講怎麼重新連結的說明文件** | 開，但當備份用，不要當主要管道 |
| 郵件名單（Mailing List） | Storage → Mailing List | 高 | 只有在客人明確同意接收行銷訊息時才勾（這是另一個獨立的同意，不能跟預約同意合併） |

**三個具體的實務建議：**

1. **每週固定看一次那張 Google Sheet，跟 email 對帳。** 如果 Sheet 的最後一筆比 email 的最後一筆舊，就是同步斷了，回後台重新連結。這件事十分鐘，但它防止的是「客人填了表單、妳沒收到、客人以為妳不理他」——這是最貴的失誤。
2. **表單送出後的成功訊息要寫回覆時間承諾。** 例如：「已收到，我們會在 24 小時內以電話或訊息與妳確認時段。若急件請直接私訊 Instagram @hanface。」這一句話同時管理期待、也給了一條更快的路。
3. **email 通知的速度一定慢於 IG 私訊。** 妳的研究數據是「1 分鐘內回覆的 IG 私訊，轉換率是 1 小時後的 3–5 倍」。表單在物理上做不到 1 分鐘。所以表單的定位是「不想私訊的人的備選管道」，不是主管道。網站上兩條路要並列呈現，不要只給表單。

### 1.8 逐步的建置順序

這個順序跟一般人的直覺相反。一般人先做首頁，我建議**最後**做首頁。

理由：首頁是其他頁面的摘要。在其他頁面還不存在的時候做首頁，妳是在摘要一份還沒寫的文件——結果一定是「先寫首頁、再回頭改三次」。而且從 IG 來的訪客已經知道妳是誰了，他要的不是「妳是誰」，是「做什麼、多少錢、怎麼約」。

| 階段 | 做什麼 | 為什麼在這個位置 | 完成的判準 |
|---|---|---|---|
| **P0**（網站之前） | ① 網域註冊在自己名下 ② 登記 Google 商家檔案 ③ IG 轉專業帳號 ④ 品牌攝影（半天，NT$8,000–20,000） | 這四件事都不需要網站就能做，而且 ②③ 免費、① 幾百塊。攝影排在最前面是因為它的產出是後面每一頁的原料 | 手上有 30–50 張可用照片（含空間、器具、質感細節、產品靜物）；商家檔案已驗證 |
| **P1** | 開帳號、選範本、**只做樣式系統**：調色盤 5 色、三組區段主題、西文字體、中文 CSS、動畫設定 | 樣式必須先於內容。反過來做，妳會排好版面再改顏色，然後發現所有間距都要重排 | 建一個測試頁，放 H1/H2/正文/次要文字/按鈕/連結各一個，三種主題各一份，用手機看過 |
| **P2** | **服務與價格頁**（最重要的一頁） | 這是唯一直接影響營收的頁面。它也是法規風險最集中的頁面——先做，就有時間反覆修文案 | 每一個課程都有：名稱、時長、內容說明、價格（含原價錨點）、適合什麼膚況。全頁文案自己對過一次禁用詞清單 |
| **P3** | **預約／聯絡頁** ＋ 表單 ＋ 通知測試 | 有了服務頁才知道表單的「服務項目」下拉選單要放什麼 | 用自己的手機填一次表單，確認 email 通知在 5 分鐘內進到手機，且 Google Sheet 有那一筆 |
| **P4** | **法律頁**：隱私權政策（個資法六款）、服務條款、契約與審閱期說明、副作用與敏感肌告知 | 在上線前完成，不要等「有空再補」。這是唯一一組「沒做完就不該上線」的頁面 | 每一頁都能從頁尾連到；表單的勾選框連到隱私權政策 |
| **P5** | **關於／理念頁** | 這一頁最需要照片與文字功力，放在後面是因為前面做完，妳對品牌語氣已經比較有把握 | 三段以內，不超過一次滑動就能讀完 |
| **P6** | **首頁**（按 1.6 的七個區段排）＋ **頁尾** ＋ IG 區塊 ＋ 導覽列 | 現在所有材料都在，首頁只是挑選與排序 | 從首屏到頁尾，手機上滑動不超過 8 次 |
| **P7** | **效能與行動版驗收**（第四部分的檢查表）＋ 綁網域 ＋ 送 Google Search Console | 綁網域放在最後，是為了讓正式網址從第一天就是完成品——搜尋引擎的第一印象只有一次 | 第四部分的表格全部打勾 |
| **P8**（上線後兩週） | 回頭看：表單有沒有進件？IG 牆還活著嗎？手機上有沒有跑版？ | 上線不是終點，這一步是最常被跳過、也最便宜的一步 | 建一個每月 10 號的行事曆提醒 |

**一個關於進度的誠實提醒：** P1–P6 對一個非技術背景的人，合理的估計是**40–70 小時的實際工時**（不含攝影與文案思考）。如果妳一週能投入 8 小時，這是 6–9 週。如果有人告訴妳「Squarespace 一個週末就能上線」，那是指「有一個能運作的網站」，不是指「一個妳願意放在 IG bio 上的網站」。

三項需求的縮寫：**【後】** 後台自主更新、**【動】** 捲動動畫、**【IG】** IG 動態牆。

### 2.1 WordPress.com（託管版）

## 第三部分：「有 AI 助手」是否改變了自建的判斷？

這是這份文件裡最重要的一節，因為它是一個真實的判斷，而且答案不是簡單的是或否。

### 3.1 AI 改變了什麼，沒改變什麼

傳統上勸退非技術者自建網站的理由是「妳做不出來」。**這個理由現在確實失效了。** 有 AI 協助，把一個 Astro + Decap CMS + Cloudflare Pages 的網站建起來，是一個真實可達的目標。

但「勸退」的理由從來不是全部落在「做不出來」上。真正的成本結構是這樣的：

```
建造成本  ────────  AI 大幅降低了  ✓
營運成本  ────────  AI 幾乎沒有改變  ✗
```

差別在於：建造是一件**妳現在正在做、注意力充足、AI 就在旁邊**的事。營運是一件**在未來某個妳最忙的時候突然發生、而妳可能沒有 AI 在手邊**的事。

### 3.2 具體會壞的東西清單（這才是判斷的依據）

不要抽象地想「維護」，看具體項目：

| 會壞的東西 | 大概多久發生一次 | 壞掉的症狀 | 修起來難不難 |
|---|---|---|---|
| Instagram Graph API token 過期 | **每 60 天**（如果沒做自動刷新） | IG 牆停止更新（無通知） | 中——要重跑一次 Meta 的授權流程 |
| npm 依賴套件安全性警示 | 每 1–3 個月 | 沒有症狀，但 GitHub 會一直寄信給妳 | 低——但需要判斷「這個要不要理」 |
| Astro 大版本升級（breaking change） | 每 12–18 個月 | 建置（build）失敗，網站無法更新 | **高**——這是最麻煩的一項 |
| Node 版本被主機平台停止支援 | 每 12–24 個月 | 建置失敗 | 中 |
| Decap CMS 登入壞掉（OAuth 設定、Netlify Identity 政策變動） | 難以預測 | **妳無法登入後台改內容** | 中到高 |
| SSL 憑證、DNS | 少（平台自動處理） | 網站顯示「不安全」 | 低 |
| 表單服務免費層政策改變 | 難以預測 | 表單靜靜地不再送出通知 | 低 |

看這張表的方式不是「加起來多久」，而是問：

> **這些事情發生的時候，我在做什麼？**

答案通常是：在做臉、在回私訊、在進貨。而網站壞掉這件事，最糟的版本是它壞在「妳剛好在 IG 上發了一篇貼文導流」的那個下午。

### 3.3 Bus Factor：如果 AI 助手不在了

這是我要妳認真想的問題，因為它不是假設性的。以下每一種情況都會發生：

- AI 訂閱到期或妳換工具
- 對話 context 消失，新的 AI 助手不知道當初為什麼那樣寫
- 妳三年後找一個工程師接手，對方看到的是「一個 AI 寫的、沒有文件的專案」

**在 Squarespace 上，網站壞掉時妳手上有：** 一個客服信箱、一個中文社群、一個「這個問題別人也遇過」的高機率。

**在自建站上，網站壞掉時妳手上有：** 一個 Git repo，和一個妳看不懂的錯誤訊息。

這不是說自建一定不行——是說**自建的隱含前提是「妳未來會持續有取得技術協助的管道」**。如果這個前提成立，自建是很好的選擇。如果不確定，就是在對未來的自己開一張支票。

### 3.4 Headless CMS 的可行性：具體評估

| | **Decap CMS** | **Sanity** |
|---|---|---|
| 費用 | 完全免費，無席位限制、無功能鎖 | 免費層 3 使用者、10GB，超過才付費 |
| 內容存在哪 | **妳的 Git repo**（Markdown 檔案） | Sanity 的雲端資料庫 |
| 資料主權 | **最高。** 內容就是妳 repo 裡的 .md 檔，妳打開就看得懂 | 中。要匯出，但格式是 Sanity 自己的 |
| 後台體驗 | 可接受。像一個簡化版的 WordPress | 好，比 Decap 精緻很多 |
| 登入方式 | GitHub OAuth 或 Netlify Identity（設定較麻煩，且 Netlify Identity 的長期定位不明朗） | Sanity 帳號（單純） |
| 專案健康度 | **需要注意。** Netlify 在 2023 年把它交給社群，之後開發速度明顯放緩 | 商業公司在維護，健康 |
| 對妳的關鍵風險 | 專案若最終停止維護，妳的後台會慢慢跟不上瀏覽器與依賴套件 | 免費層政策可能改變；它是一個外部服務，等於一個新的鎖定點 |

**我的判斷：如果真要走自建，選 Decap 而不是 Sanity。** 理由不是 Decap 比較好用（它不是），是因為 **Decap 的失敗模式比較溫和**。如果 Decap 的後台某天壞掉，妳的內容還在，是一堆 Markdown 檔案躺在 GitHub 上，任何工程師（或任何 AI）都能接手。如果 Sanity 出事，妳的內容在別人的資料庫裡。

自建路線的整個價值前提就是「資料主權」。用一個雲端 CMS 把內容鎖回別人手上，等於付出了自建的所有成本，卻沒拿到自建的主要好處。

### 3.5 我的傾向，以及一個能讓妳自己決定的實驗

**我的傾向：這個階段選 Squarespace，但用「自建的紀律」來經營內容。**

具體意思是——即使網站在 Squarespace 上，妳仍然要：

1. 所有文案寫在自己的 Google Docs 或一個資料夾裡的 .md 檔，Squarespace 上的只是副本
2. 所有圖片原檔留在自己的雲端硬碟，用一致的檔名規則
3. 色票、字級、間距規範寫成一份文件（就是 docs 這個資料夾）
4. 網域、GA4、Search Console、Google 商家檔案全部用妳自己的 Google 帳號建

這樣做的話，**平台鎖定的實際代價會小到幾乎不重要**。因為妳被鎖住的只有「版面排列」——而三年後妳本來就會想重排版面。

理由是：妳現在最大的瓶頸是**照片素材**，不是平台。花 40 小時學自建，換來的是每年省 NT$8,000；同樣的 40 小時如果用來想文案、拍照、經營 IG，價值高得多。自建省下的錢（五年約 NT$38,000）確實是真金白銀，但它是用「未來會壞的東西」換來的，而妳現在的狀態不適合再多背一個會壞的東西。

**在什麼條件下我會改變建議：**

1. 妳（或家人／伴侶／固定合作的人）本來就有寫程式的習慣 → 直接選 Astro，省下的錢很值得
2. 妳三個月後回來說「Squarespace 我用不順、想改的地方一直改不到」→ 那就不是平台選錯，是需求比想像複雜，這時 Astro 反而合理
3. 妳的網站流量成長到「效能差距真的在影響轉換」→ 這通常要月訪客上千才明顯，屆時再遷移，那時妳也有預算請人做

**最後給妳一個可以自己做的決策實驗（我認為這比聽我的建議更有用）：**

> 花一個週末，用 AI 幫妳建一個 Astro + Decap 的測試站，隨便什麼內容都好。
>
> 建好之後，**關掉 AI**。
>
> 然後試著自己做這三件事：
> 1. 把首頁的一行字從「A」改成「B」，並讓改動出現在線上
> 2. 換掉一張圖片
> 3. 新增一個頁面
>
> 如果三件事妳都能在 30 分鐘內獨立完成 → 選 Astro，妳會省很多錢，而且妳有能力。
> 如果卡在任何一件 → 選 Squarespace，NT$8,800/年 買的是「不用卡住」。

這個實驗的成本是一個週末，它能省下的是三年的猶豫。而且**不管結果如何妳都不虧**：如果選了 Squarespace，妳也已經知道自建長什麼樣子，日後跟外包溝通時說話有底氣。

## 第四部分：效能預算與檢查方法

### 4.1 目標數字

| 指標 | 目標 | 及格線 | 為什麼是這個數字 |
|---|---|---|---|
| **LCP**（最大內容繪製，手機） | **≤ 2.5 秒** | ≤ 4.0 秒 | 2.5s 是 Google Core Web Vitals 的「良好」門檻。**誠實說：Squarespace 上要達到 2.5s 需要很用力**，一般落在 2.5–4s。Astro 能做到 1.5s 以下 |
| **CLS**（版面位移） | ≤ 0.1 | ≤ 0.25 | 這一項妳完全控制得到——只要不亂塞第三方 script、圖片都有明確尺寸 |
| **INP**（互動反應） | ≤ 200ms | ≤ 500ms | 靜態的品牌網站通常自然過關 |
| 首屏總傳輸量 | ≤ 1.2 MB | ≤ 2 MB | 這是妳唯一能直接操作的槓桿 |
| 首屏主視覺單張 | **≤ 250 KB** | ≤ 400 KB | 手機隨拍原檔通常 3–6 MB，也就是 **12–24 倍超標**。這是目前最可能拖垮妳網站的單一因素 |
| 中文字型檔載入量 | **0 KB** | 0 KB | 走系統字體，這一項不容妥協 |

### 4.2 圖片規格建議

| 用途 | 長邊像素 | 格式 | 目標檔案大小 |
|---|---|---|---|
| 滿版主視覺（首屏、區段背景） | 2000 px | WebP | ≤ 250 KB |
| 半幅／並排圖片 | 1200 px | WebP | ≤ 120 KB |
| 服務卡片、縮圖 | 800 px | WebP | ≤ 80 KB |
| IG 牆（原生區塊自動處理） | 不用管 | — | — |
| Logo | SVG（若有向量檔）；否則 PNG 長邊 600px | SVG / PNG | ≤ 30 KB |

**兩個重點：**

1. **Squarespace 會自動幫妳產生多種尺寸與 WebP 版本，但它是從妳上傳的檔案切的。** 所以「反正平台會處理」是錯的——上傳 6MB 的原檔，會讓後台變慢、讓妳的儲存空間爆掉，而且平台切出來的最大尺寸仍然可能過重。**先壓再上傳，一定要做。**
2. **不要上傳長邊超過 2500px 的圖。** 手機螢幕邏輯寬度大多在 390–430px，就算是 3 倍像素密度也只需要約 1300px。2000px 已經有充足餘裕。

### 4.3 圖片壓縮流程（非技術人員可執行）

**建議工具：Squoosh（https://squoosh.app）** ——免費、瀏覽器內執行、**圖片不會上傳到任何伺服器**（這一點對客人的照片很重要）。

步驟：

1. 開 https://squoosh.app
2. 把一張照片拖進視窗
3. 右側面板：
   - 格式下拉選 **WebP**
   - `Quality` 拉到 **75**（韓系柔和調性的照片，75 幾乎看不出差別；如果是有細緻紋理的產品特寫，拉到 82）
   - 勾 `Resize`，`Width` 填 **2000**（或按上表的尺寸），`Maintain aspect ratio` 保持勾選
4. 看左下角顯示的檔案大小與縮減百分比。**如果還超過 250 KB，把 Quality 降到 65 再看一次**
5. 按右下角下載鈕
6. **改檔名再上傳**，規則：`hanface-` ＋ 內容英文描述 ＋ 兩位數編號，全小寫、用連字號。例如 `hanface-treatment-room-01.webp`、`hanface-cleansing-detail-02.webp`

第 6 步不是龜毛。檔名會被 Google 讀進去當 SEO 訊號，而且半年後妳要找「那張洗手台的照片」時，`hanface-basin-detail-03.webp` 跟 `IMG_4821.HEIC` 的差別會非常明顯。

**替代工具：**
- **TinyPNG**（https://tinypng.com）：一次最多 20 張，單檔 5MB 上限。優點是批次；缺點是圖片會上傳到他們伺服器，而且無法調尺寸
- **Mac 內建**：`預覽程式` → 選多張 → `工具` → `調整大小` → 設長邊 2000 → 匯出。可以批次改尺寸，但格式選項沒有 WebP（只能存 JPEG，檔案會大 25–35%）
- **iPhone 拍照設定**：先進 `設定` → `相機` → `格式`，**確認是「高效率」（HEIF）而不是「最相容」**。HEIF 檔小很多，Squoosh 也讀得懂

**一個實際的工作流建議：** 建兩個資料夾，`01-原檔` 和 `02-網站用`。原檔永遠不動（日後印刷、重新裁切都要用），只有 `02-網站用` 裡的檔案會被上傳。這個習慣會在妳第一次需要一張大圖印海報時救妳一次。

### 4.4 自己檢查的方法（三層，由粗到細）

**第一層：真機測試（最重要，也最常被跳過）**

1. 拿自己的手機
2. **關掉 Wi-Fi，用行動網路**
3. 完全關掉瀏覽器再重開（避免快取）
4. 貼上網址，**心裡數秒**
5. 判準：**主視覺在 3 秒內出現了嗎？**

這一層比任何工具重要，因為它測的是妳客人的真實體驗。工具會給妳分數，真機給妳感覺，而轉換率跟感覺相關。

**第二層：PageSpeed Insights（免費）**

1. 開 https://pagespeed.web.dev
2. 貼上網址，按 `Analyze`
3. **只看 `Mobile`（行動裝置）分頁**——妳 90% 的流量在手機，桌機分數好看沒有意義
4. 只看三件事，其他全部忽略：
   - 上方的 **Core Web Vitals 三個燈**（LCP / CLS / INP）是綠的嗎？
   - `Largest Contentful Paint element` 這一項展開來，**它指出的是哪一張圖／哪一段文字？** 那就是妳要優先優化的目標
   - `Opportunities` 裡有沒有 `Properly size images` 或 `Serve images in modern formats`——有的話，就是還有圖片沒壓好

**忽略總分那個 0–100 的數字。** Squarespace 網站的行動版總分經常是 40–60，而 Core Web Vitals 三項全綠。總分包含很多妳在託管平台上無法控制的項目，盯著它只會讓妳焦慮又無能為力。三個燈才是 Google 真的用來排名的東西。

**第三層：手機實機的 Chrome DevTools（進階，有需要再用）**

Mac + iPhone 用 Safari 的「網頁檢閱器」，Windows + Android 用 Chrome 的 `chrome://inspect`。這一層通常只在前兩層抓到問題、要找原因時才需要。

### 4.5 上線驗收表（P7 階段逐項打勾）

| 檢查項 | 通過標準 |
|---|---|
| 真機 4G 冷啟動 | 主視覺 3 秒內出現 |
| PageSpeed 行動版 Core Web Vitals | LCP / CLS / INP 三燈全綠（或至少 LCP ≤ 4s、CLS ≤ 0.1） |
| 圖片檔案大小 | 沒有任何一張超過 400 KB |
| 中文字型 | 網路面板裡沒有任何 .woff/.woff2 中文字型（檔案 > 1MB 的字型檔） |
| 手機直向 | 每一頁都不需要左右橫向滑動 |
| 文字對比度 | 全站沒有淺藕（`#E2B4A6`）上放字的地方 |
| 連結可辨識 | 藕色面上的連結都有底線 |
| 表單實測 | 自己填一次，5 分鐘內手機收到通知，Google Sheet 有紀錄 |
| IG 牆 | 顯示的是最近 7 天內的貼文（不是空白、不是半年前） |
| 法律頁 | 隱私權政策、服務條款、契約審閱期說明都能從頁尾連到 |
| 禁用詞掃描 | 用瀏覽器 Ctrl+F 在每一頁搜尋：療程、換膚、痘疤、淡斑、拉提、抗老、醫美、保證、100%、最有效——結果都是 0 筆 |
| 法規整體觀感 | 找一個不認識妳的朋友看網站，問他一句話：「妳覺得這是醫美診所還是護膚工作室？」如果他說診所，就要改 |

最後那兩項是整份驗收表裡最重要的。因為主管機關的認定方法是「整體綜合表現評價」，不是關鍵字比對。Ctrl+F 只能抓字，最後那個朋友測試才抓得到「整體印象」。

## 第五部分：搬家風險與資料主權

### 5.1 三年後想搬家，實際會損失什麼

Squarespace 的匯出功能會給妳一個 WordPress 格式的 .xml 檔。它**不包含**：

| 損失的東西 | 損失程度 | 能不能補救 |
|---|---|---|
| 所有版面排列（Fluid Engine 排的內容尤其無法匯出） | **全損** | 不能。要重排 |
| 所有樣式設定（調色盤、字體、間距、動畫）與自訂 CSS | **全損** | 不能匯出，但妳的色票文件在手上，可以重建 |
| 頁面專屬的頁首／頁尾 | 全損 | 重做 |
| 圖片 | 只匯出**連結**，不是檔案本身 | **可以完全避免**——只要妳的圖片原檔留在自己電腦裡 |
| 商店頁、多個部落格、影音區塊、行事曆頁、作品集頁 | 不匯出 | 重做 |
| 表單投稿紀錄 | 可另外下載 CSV（表單投稿是可以匯出的） | 可以。但要記得做 |
| 網域 | 不會損失（域名可轉移），**除非它註冊在別人名下** | 見 5.3 |
| SEO 排名 | 有短期波動風險 | 做好 301 轉址可以大幅降低 |

**一個誠實標註：** 關於「Squarespace 7.1 是否支援 XML 匯出」，第三方資料來源說法互相矛盾——有的說 7.1 完全不支援匯出，有的說支援但 Fluid Engine 內容除外。**我無法連上官方說明頁驗證。** 實務上的正確假設是：**假設妳幾乎匯不出任何有用的東西，然後自己另外留備份。** 這個假設如果錯了，妳只是多做了一點功；如果對了，它救了妳。

### 5.2 降低損失的六件事（現在就做，成本接近零）

| 做什麼 | 怎麼做 | 為什麼 |
|---|---|---|
| ① 網域註冊在自己名下、且**不要買在 Squarespace** | 見第六部分 | 這是唯一一項「做錯了幾乎無法補救」的事 |
| ② 所有文案留在 Squarespace 之外 | Google Docs 或 `docs/` 資料夾裡的 .md 檔。**Squarespace 上的是副本，不是正本** | 文案是妳花最多腦力的資產，它不該只存在別人的資料庫裡 |
| ③ 所有圖片原檔留在自己的雲端硬碟 | `01-原檔` / `02-網站用` 兩層資料夾，一致的檔名規則 | 匯出功能只給圖片連結。平台一停，連結就死 |
| ④ 樣式規範寫成文件 | 就是 `docs/` 這個資料夾。色票、字級、行高、三組主題規則都寫下來 | 這是「重建」跟「重新設計」的差別。有規範，重建一個新平台的樣式只要兩小時 |
| ⑤ Google 相關資產全部用自己的帳號 | Google 商家檔案、GA4、Search Console、Google Sheet 表單備份 | 這些是**跨平台的資產**，跟網站在哪裡完全無關。這也是為什麼商家檔案不用等網站——它的價值獨立於網站存在 |
| ⑥ 每季匯出一次 | Settings → Import/Export → Export（拿 XML）＋ 每張表單下載 CSV。存到雲端硬碟，檔名帶日期 | 十分鐘的事。它防止的是「平台帳號因為刷卡失敗被停用」這種低機率但高損失的情況 |

### 5.3 一個關於「平台鎖定」的誠實反面觀點

平台鎖定的恐懼常常被誇大，我想給妳一個對稱的視角。

問一個問題：**三年後，妳真的會想把現在這個網站原封不動搬到別的平台嗎？**

大概不會。三年後妳會有專業攝影、有明確的差異化定位、有真實的客人回饋、可能有中文品牌名、可能已經開了線上預約。**那時妳想要的是一個新網站，不是舊網站的搬家。**

所以真正不可替代的資產只有四樣：

```
網域          ── 只要在妳名下，就永遠是妳的
內容（文案＋照片） ── 只要有自己的備份，就永遠是妳的
客戶名單      ── 從來就不在網站上，在妳的手機跟預約系統裡
Google 商家檔案與評論 ── 從來就不在網站上，在 Google 上
```

**這四樣東西，沒有一樣是被 Squarespace 鎖住的**——只要妳照 5.2 做。被鎖住的是「版面排列」，而那是三年後妳本來就要丟掉的東西。

這是我為什麼認為在妳的情境下，平台鎖定不足以構成選擇自建的理由。**但 Wix 是例外**——Wix 連殘缺的匯出都沒有，而且它的封閉性是設計上的選擇。如果妳最後選 Wix，5.2 的六項要做得更嚴格。

## 第六部分：網域設定的實際步驟

### 6.1 hanface.tw 的查詢結果與查詢途徑

我在 **2026 年 8 月 17 日** 透過網域查詢 API 查到的結果：

| 網域 | 狀態 | 參考價格 |
|---|---|---|
| **hanface.tw** | **顯示可註冊** | 價格查詢失敗（API 回錯），需自行確認 |
| **hanface.com.tw** | **顯示可註冊** | 約 US$21／首年 |
| hanface.co | 可註冊 | 約 US$4.99／首年（該來源價格；先前查到的是首年 NT$553／續約 NT$1,107，價差來自不同註冊商的首年促銷） |
| hanface.beauty | 可註冊 | 約 US$1.99／首年 |
| hanfaceskin.com | 可註冊 | 約 US$11.25／首年 |
| hanface.com | 已被註冊（既有資訊） | — |

**必須自己再驗一次的理由：** 這個查詢走的是第三方註冊商的 API，`.tw` 這種國碼網域的可用性判斷有時不準確（尤其 API 對 hanface.tw 的價格查詢回了錯誤，這通常代表該註冊商對 .tw 的支援不完整）。**唯一權威的來源是 TWNIC。**

**hanface.tw 的權威查詢途徑：**

1. **TWNIC 官方 whois**：https://rs.twnic.tw/ （TWNIC 是 `.tw` 與 `.台灣` 的註冊管理機構）
2. **TWNIC 受理註冊機構清單**：TWNIC 官網 https://twnic.tw 有列出所有合法的 `.tw` 受理註冊機構。台灣常見的包括 **網路中文（Net-Chinese）**、**中華電信 HiNet**、**PChome 註冊網**。這些的優點是繁中介面、有台灣客服、可開統一發票（對日後報稅有用）
3. **國際註冊商也支援 .tw**：Gandi（有中文介面，約 US$24/年）、Dynadot（約 US$18/年）

`.tw` 自 2006 年起註冊已無資格限制，任何人都可以註冊，不需要台灣公司登記。

### 6.2 .tw 還是 .com.tw 還是 .co？我的建議

| 選項 | 優點 | 缺點 |
|---|---|---|
| **hanface.tw**（推薦） | 短、好記、好念。台灣消費者對 `.tw` 的信任度高。IG bio 空間有限，短網址是實質優勢 | 比 `.com` 貴（約 NT$800–1,200/年 vs 約 NT$400/年） |
| hanface.com.tw | 「像正式公司」的觀感最強 | 多四個字元，在 IG bio 與口頭傳達上都比較累 |
| hanface.co | 便宜、國際感 | 台灣消費者會習慣性打成 `.com`，然後到別人的網站去。**這是真實的流量漏損** |
| hanface.beauty | 最便宜 | 新 gTLD，台灣消費者陌生；部分企業郵件系統對新 gTLD 的信任分數較低，日後寄信容易進垃圾信匣 |

**我的建議組合：**

1. **主網域註冊 `hanface.tw`**（若 TWNIC 確認可註冊）
2. **同時註冊 `hanfaceskin.com`** 當防禦與備援（約 NT$400/年），設 301 轉址到主網域。理由：`.com` 是所有人的肌肉記憶，而且它是妳未來想做英文／海外時的資產
3. **不要把 `hanface.beauty` 當主網域**，如果要買也只當防禦

總網域成本估計：約 **NT$1,200–1,600／年**。

### 6.3 為什麼註冊人（Registrant）一定要是妳本人

這一項我要講得重一點，因為它是這整份文件裡**唯一一個做錯了幾乎無法補救**的環節。

網域的「註冊人」（Registrant）是法律上的持有人。不是「誰付錢」，不是「誰在管」，是 whois 紀錄上寫的那個人。

**做錯會發生什麼（這在台灣中小企業非常常見）：**

- 設計師／外包／前員工好心「幫妳一起買了」，網域掛在他的帳號、他的 email 底下
- 兩年後合作結束、聯絡不上、或雙方鬧翻
- 妳想把網站搬到別的平台，需要 **EPP 授權碼（transfer code）**——只有帳號持有人拿得到
- 妳想改 DNS 指向新主機——只有帳號持有人能改
- 結果：**妳在租用自己的品牌名稱**，而房東不接電話

網域是妳所有數位資產的根。IG 帳號可以重開，網站可以重做，但網域一旦落在別人手上，妳能做的只有花錢買回來（對方要多少是他說），或改一個品牌名。

**具體怎麼做對：**

1. 註冊時**用妳自己的 email 和信用卡**，帳號密碼只有妳知道
2. 註冊完成後，去 whois 查一次自己的網域，確認 `Registrant Name` / `Registrant Email` 是妳（部分註冊商會開隱私保護遮罩，那就登入自己的帳號後台確認）
3. **開啟兩步驟驗證（2FA）** 和 **網域鎖定（Registrar Lock / Transfer Lock）**——這兩項免費，防止被盜轉
4. 註冊人的 email **不要用會過期的 email**（不要用公司或前雇主的信箱）。用 Gmail
5. **把續約日寫進行事曆，並開自動續約。** 網域過期被別人搶註是最痛的一種失誤，而且通常搶註的是專門盯著這個的投機者，要買回來的價格是四位數美金起跳
6. 如果有人幫妳建站，他需要的是**DNS 修改權限或後台協作者身分**，**不是網域所有權**。這兩件事完全可以分開，而且應該分開

（`.tw` 另有 TWNIC 提供的「域名註冊鎖（Registry Lock）」加值服務，2026 年促銷價 NT$4,800／首年。這是給高價值品牌的等級，**妳現階段不需要**，第 3 點的免費註冊商鎖定就足夠。）

### 6.4 DNS 怎麼指到 Squarespace

有兩種做法，我建議第二種。

**做法一：交出 Nameserver（最簡單）**

在註冊商後台把 nameserver 改成 Squarespace 提供的四組值。優點是一次設定完，Squarespace 全部幫妳處理。**缺點是妳的 DNS 主權交給了 Squarespace**——日後要加一筆記錄（例如驗證 Google Workspace 信箱、加一個子網域），都得在 Squarespace 的介面裡做，而如果哪天 Squarespace 帳號有問題，妳的 email 也會一起受影響。

**做法二：保留自己的 DNS，只加記錄（建議）**

DNS 留在註冊商（或搬到 Cloudflare 的免費 DNS，介面比大多數註冊商好），只加指向 Squarespace 的記錄。這樣**網域、DNS、網站是三個獨立的層**，換網站不影響 email，Squarespace 出事不影響網域。

步驟：

1. Squarespace 後台 → `設定（Settings）` → `網域（Domains）` → `使用我擁有的網域（Use a domain I own）`
2. 輸入 `hanface.tw`，Squarespace 會顯示一組要新增的記錄。通常是：
   - **4 筆 A 記錄**：Host 為 `@`（或空白），指向 4 個 IP 位址
   - **1 筆 CNAME 記錄**：Host 為 `www`，指向 `ext-cust.squarespace.com`
   - **1 筆 CNAME 驗證記錄**：Host 是一串隨機字元，Value 也是一串隨機字元（用來證明網域是妳的）
3. 到註冊商（或 Cloudflare）的 DNS 面板，逐筆新增
4. 等待生效。通常 30 分鐘到 4 小時，**最多 48 小時**
5. 回 Squarespace 按 `Verify`（驗證）
6. 驗證通過後，在 Squarespace 設定「主要網域」為 `hanface.tw`，並確認 `www` 自動轉到主網域（或反過來，選一個就好，不要兩個都能開——那會分散 SEO 權重）
7. 確認 SSL 憑證已自動簽發（Squarespace 會自動處理，通常 24 小時內）。開網站看網址列有沒有鎖頭

**兩個重要提醒：**

- **上面的記錄值一定要用 Squarespace 後台當下顯示的數值，不要照抄網路教學文章裡的 IP。** Squarespace 換過 IP，網路上有大量過期的教學文，照抄會導致網站連不上，而且症狀（「連不到」）跟「DNS 還沒生效」完全一樣，妳會等兩天才發現是抄錯。
- **如果 DNS 搬到 Cloudflare，Proxy（橘色雲朵）要關掉**，設成 DNS only（灰色雲朵）。開著 proxy 會跟 Squarespace 的 SSL 憑證流程衝突。

### 6.5 註冊商選擇

| 註冊商 | 支援 .tw | 特點 | 適合 |
|---|---|---|---|
| **網路中文 / HiNet / PChome 註冊網** | 是 | 繁中介面、台灣客服、可開統一發票 | **`.tw` 的首選。** 妳如果日後要報帳，發票這件事有價值 |
| **Gandi** | 是 | 有中文介面，隱私保護內建免費，介面乾淨 | 想同時管 `.tw` 和 `.com` 在同一個地方 |
| **Cloudflare Registrar** | **不支援 `.tw`**（據我所知，請以其當下支援清單為準） | 只收成本價、無首年誘餌、續約不漲價、DNS 全球最快 | `.com` / `.co` 的最佳選擇 |
| **Squarespace 內建網域** | 不確定是否支援 `.tw` | 最方便（一站搞定），首年通常免費 | **不建議。** 把網域跟網站綁在同一家，是把兩個獨立的風險綁成一個 |

**我的建議：`hanface.tw` 買在台灣的 TWNIC 受理註冊機構（發票 + 中文客服），`hanfaceskin.com` 買在 Cloudflare（便宜、續約不漲）。DNS 統一搬到 Cloudflare 管理。**

這個組合聽起來麻煩，但它只在第一天麻煩，之後三年都不用碰。而它換來的是「網域 / DNS / 網站」三層完全獨立——這是資料主權最實際的形式。
